## Глава 1. Теоретический фундамент: сравнения против линейных алгоритмов

### 1.1. Информационно-теоретический предел сортировок сравнением $\Omega(n \log n)$

> **Вопрос преподавателя:** *«Почему ни один алгоритм сортировки, основанный на сравнениях, не может работать быстрее $\Omega(n \log n)$ в худшем и среднем случаях? Можно ли отсортировать быстрее?»*

#### Строгое доказательство через модель дерева решений (Decision Tree):
1. **Модель вычислений:** Любой алгоритм сортировки, использующий попарные сравнения элементов ($a[i] \lessgtr a[j]$), можно представить как бинарное дерево решений.
   - Каждая внутренняя вершина дерева — это одна операция сравнения.
   - Переходы влево/вправо соответствуют исходам `True` / `False`.
   - В листьях дерева располагаются окончательные перестановки элементов исходного массива.
2. **Число листьев:** Массив из $n$ различных элементов имеет ровно $n!$ возможных перестановок. Чтобы алгоритм правильно работал на любом входе, каждый возможный порядок должен соответствовать хотя бы одному листу. Значит, число листьев $L \ge n!$.
3. **Высота дерева $h$ (худшее число сравнений):** Бинарное дерево высоты $h$ содержит не более $2^h$ листьев:
   $$ 2^h \ge L \ge n! \implies h \ge \log_2(n!) $$
4. **Приближение Стирлинга:** Логарифм факториала оценивается снизу:
   $$ \log_2(n!) = \sum_{i=1}^n \log_2 i \ge \sum_{i=\lceil n/2 \rceil}^n \log_2 i \ge \frac{n}{2} \log_2\left(\frac{n}{2}\right) = \Omega(n \log n) $$
5. **Вывод:** Высота дерева $h = \Omega(n \log n)$. Любой алгоритм сортировки сравнениями (MergeSort, HeapSort, QuickSort, Timsort) обязан в худшем и среднем случаях совершать не менее $\Omega(n \log n)$ сравнений.

#### Как CountingSort и RadixSort обходят этот предел?
- Они **НЕ сравнивают элементы друг с другом**!
- Они выходят за рамки модели дерева решений и используют **цифровую (адресную) природу ключей**: числовое значение ключа напрямую используется как **индекс ячейки массива**, доступ к которому в памяти RAM выполняется за $O(1)$.
- Это позволяет достичь линейного времени $O(n + k)$ или $O(d \cdot (n + b))$.

## Глава 2. Детальный разбор каждого алгоритма

### 2.1. Сортировка слиянием (`merge_sort`) со стабильным слиянием

```python
def merge(left: list, right: list, key=None) -> list:
    kfn = key if key is not None else (lambda x: x)
    merged = []
    i = 0
    j = 0
    len_left = len(left)
    len_right = len(right)

    while i < len_left and j < len_right:
        # Условие <= обеспечивает стабильность:
        # При равенстве ключей элемент из левой половины берётся первым!
        if kfn(left[i]) <= kfn(right[j]):
            merged.append(left[i])
            i += 1
        else:
            merged.append(right[j])
            j += 1

    if i < len_left:
        merged.extend(left[i:])
    if j < len_right:
        merged.extend(right[j:])

    return merged


def merge_sort(a: list, key=lambda x: x) -> list:
    if len(a) <= 1:
        return list(a)
    kfn = key if key is not None else (lambda x: x)
    mid = len(a) // 2
    left = merge_sort(a[:mid], key=kfn)
    right = merge_sort(a[mid:], key=kfn)
    return merge(left, right, key=kfn)
```

#### Что делает алгоритм:
Реализует парадигму «Разделяй и властвуй». Делит массив пополам на левую и правую части, рекурсивно сортирует каждую из них, после чего объединяет отсортированные половинки с помощью двух указателей в процедуре `merge()`.

#### Построчный разбор и инварианты:
1. `if len(a) <= 1: return list(a)` — базовый случай рекурсии. Пустой список или срез длины 1 уже тривиально упорядочен.
2. `mid = len(a) // 2` — точка деления строго пополам.
3. `merge(left, right)`: два указателя `i` и `j` бегут по отсортированным спискам. На каждом шаге меньший элемент дописывается в `merged`.
4. **Инвариант стабильности:** условие `if kfn(left[i]) <= kfn(right[j]):` строго сохраняет порядок одинаковых ключей: элемент из левой части стоял в исходном массиве раньше, поэтому он обязан попасть в `merged` первым.

#### Сложность:
- **Время:** строго $\Theta(n \log n)$ во ВСЕХ случаях (лучший, средний, худший). Рекуррентность $T(n) = 2T(n/2) + \Theta(n)$. По Master Theorem (случай 2): $T(n) = \Theta(n \log n)$.
- **Память:** $\Theta(n)$ — на каждом уровне рекурсии создаются новые списки срезов и объединения.

### 2.2. Устойчивая сортировка подсчётом (`counting_sort`)

```python
def counting_sort(a: list[int], key_max: int) -> list[int]:
    if not a:
        return []
    if key_max < 0:
        raise ValueError("key_max должен быть неотрицательным")

    # Фаза 1: Подсчёт частот
    count = [0] * (key_max + 1)
    for x in a:
        count[x] += 1

    # Фаза 2: Префиксные суммы
    for i in range(1, len(count)):
        count[i] += count[i - 1]

    # Фаза 3: Устойчивая расстановка элементов С КОНЦА
    res = [0] * len(a)
    for x in reversed(a):
        count[x] -= 1
        res[count[x]] = x

    return res
```

#### Что делает алгоритм (3 фазы):
1. **Фаза 1 (Подсчёт частот, $O(n)$):** массив `count` размера $k = \text{key\_max} + 1$ подсчитывает количество вхождений каждого числа `x`.
2. **Фаза 2 (Префиксные суммы, $O(k)$):** кумулятивное суммирование `count[i] += count[i - 1]`. Теперь `count[x]` хранит количество элементов, меньших либо равных `x`. Это в точности правая граница индексов для размещения числа `x` в результирующем массиве.
3. **Фаза 3 (Расстановка, $O(n)$):** обходим входной массив **СТРОГО С КОНЦА** (`reversed(a)`): уменьшаем `count[x] -= 1` и записываем `res[count[x]] = x`.

#### Почему обход строго с конца (reversed)?
> Если во входе есть несколько одинаковых чисел `x`, то число, стоящее ближе к концу массива, при обратном обходе обработается первым и встанет на позицию `count[x] - 1`. Предшествующее ему такое же число встанет на позицию `count[x] - 2`. Исходный порядок дубликатов полностью сохранён! Сортировка **стабильна**.

#### Границы применимости:
- При $k \le n$ (узкий диапазон, например $k = 100$ при $n = 100\,000$): время $O(n)$, феноменальная скорость (в 25 раз быстрее MergeSort!).
- При $k \gg n$ (широкий диапазон, например $k = 10^9$): попытка создать массив `count = [0] * (10**9 + 1)` требует $\approx 8$ ГБ оперативной памяти и $10^9$ итераций, что приводит к `MemoryError`. На таком входе CountingSort абсолютно неприменим!

### 2.3. Поразрядная сортировка (`radix_sort_lsd`)

```python
def radix_sort_lsd(a: list[int]) -> list[int]:
    if len(a) <= 1:
        return list(a)
    max_val = max(a)
    if max_val < 0:
        raise ValueError("radix_sort_lsd поддерживает только неотрицательные целые числа")
    if max_val == 0:
        return list(a)

    res = list(a)
    exp = 1       # Множитель текущего разряда (1, 10, 100, 1000...)
    base = 10     # Основание системы счисления (десятичная)

    while max_val // exp > 0:
        count = [0] * base
        for x in res:
            digit = (x // exp) % base
            count[digit] += 1

        for i in range(1, base):
            count[i] += count[i - 1]

        out = [0] * len(res)
        for x in reversed(res):
            digit = (x // exp) % base
            count[digit] -= 1
            out[count[digit]] = x

        res = out
        exp *= base

    return res
```

#### Что делает алгоритм:
Сортирует неотрицательные числа поразрядно от младшего разряда (LSD — Least Significant Digit, единицы) к старшим (десятки, сотни, тысячи...). На каждом разряде запускается устойчивая сортировка подсчётом по текущей цифре `(x // exp) % base`.

#### Почему поразрядный проход ОБЯЗАН быть устойчивым (стабильным)?
> К началу обработки $j$-го разряда массив уже упорядочен по суффиксу из $j-1$ младших цифр (инвариант алгоритма). Если два числа имеют одинаковую цифру в $j$-м разряде, их правильный взаимный порядок полностью определяется их младшими разрядами. Устойчивость процедуры подсчёта гарантирует сохранение этого порядка.  
> Если бы проход был неустойчивым (например, прямой обход вместо обратного), элементы с равными текущими цифрами перемешались бы, полностью разрушив результат сортировки по всем предыдущим разрядам!

#### Сложность:
- Время: $\Theta(d \cdot (n + b))$, где $d = \lceil \log_{10}(\text{max\_val} + 1) \rceil$, $b = 10$. Для 32-битных чисел $d \le 10$, поэтому на практике алгоритм ведёт себя как строго линейный $\Theta(n)$.
- Память: $\Theta(n + b)$ (буферный массив `out` плюс 10 счётчиков цифр).

### 2.4. Пирамидальная сортировка (`heap_sort`) in-place

```python
def sift_down(a: list[int], i: int, n: int) -> None:
    while True:
        left = 2 * i + 1
        right = 2 * i + 2
        largest = i

        if left < n and a[left] > a[largest]:
            largest = left
        if right < n and a[right] > a[largest]:
            largest = right

        if largest != i:
            a[i], a[largest] = a[largest], a[i]
            i = largest
        else:
            break


def heap_sort(a: list[int]) -> None:
    n = len(a)
    if n <= 1:
        return

    # Фаза 1: Построение max-кучи за строго O(n)
    for i in range((n - 2) // 2, -1, -1):
        sift_down(a, i, n)

    # Фаза 2: Извлечение максимумов за O(n log n)
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]
        sift_down(a, 0, end)
```

#### Что такое двоичная max-куча в массиве:
Двоичное дерево упаковывается в плоский массив без ссылочных объектов:
- Для вершины с индексом $i$:
  - Левый ребёнок: `2 * i + 1`
  - Правый ребёнок: `2 * i + 2`
  - Родитель: `(i - 1) // 2`
- **Свойство max-кучи:** значение любого узла не меньше значений его детей: $a[i] \ge a[2i+1]$ и $a[i] \ge a[2i+2]$.

#### Почему построение кучи (Heapify) работает за $O(n)$, а не за $O(n \log n)$?
> Мы обходим внутренние узлы снизу вверх: от последнего нелистового узла `(n - 2) // 2` до корня `0`.  
> Узлы на нижних уровнях кучи имеют малую высоту спуска:
> - $n/2$ листьев вообще не просеиваются (высота 0).
> - $n/4$ узлов просеиваются максимум на 1 уровень.
> - $n/8$ узлов просеиваются максимум на 2 уровня.
> 
> Суммарное число операций:
> $$ S = \sum_{h=0}^{\lfloor \log_2 n \rfloor} \frac{n}{2^{h+1}} \cdot h = \frac{n}{2} \sum_{h=0}^\infty \frac{h}{2^h} $$
> Сумма ряда $\sum_{h=0}^\infty \frac{h}{2^h} = 2$. Подставляя, получаем:
> $$ S = \frac{n}{2} \cdot 2 = n = O(n) $$
> Фаза построения кучи строго линейна!

#### Почему HeapSort проигрывает QuickSort на практике?
Оба алгоритма имеют асимптотику $O(n \log n)$, но HeapSort уступает по константе в $1.5 - 2$ раза из-за **плохой пространственной локальности ссылок (L1/L2 Cache Misses)**:
- В QuickSort массив обходится последовательными блоками слева направо (отличный кэш).
- В HeapSort процедура `sift_down` прыгает по степеням двойки: $i \to 2i+1 \to 4i+3 \to \dots$, каждый раз обращаясь к совершенно разным строкам оперативной памяти, что непрерывно выбивает кэш процессора.

### 2.5. Сортировка Timsort (`sorted()` из стандартной библиотеки)

#### Как устроен алгоритм:
1. **Адаптивность к естественной упорядоченности:** алгоритм сканирует массив, отыскивая уже упорядоченные участки данных — монотонные неубывающие или строго убывающие цепочки (runs).
2. **Бинарные вставки:** если найденный участок короче `minrun` (обычно 32–64 элемента), он дополняется следующими элементами и досортировывается с помощью `insertion_sort` с бинарным поиском позиции.
3. **Слияние цепочек:** найденные участки помещаются в стек и объединяются по правилам, похожим на MergeSort, с оптимизацией «галопа» (galloping mode).
4. **Итог:** на полностью упорядоченном массиве Timsort делает один линейный проход проверки за $\Theta(n)$ и время $0.0004$ с на $n = 100\,000$ (в 600 раз быстрее обычного MergeSort!).

## Глава 3. Банк каверзных вопросов преподавателя на защите

### Вопрос 1. «Почему в CountingSort массив счётчиков создаётся размера `key_max + 1`, а не `key_max`?»
- **Ответ:** «Индексация массивов в Python начинается с 0. Если максимальный ключ равен `key_max`, то для возможности обращения по индексу `count[key_max]` размер массива обязан быть не менее `key_max + 1`, иначе произойдёт ошибка `IndexError: list index out of range`».

### Вопрос 2. «В чём заключается различие между LSD и MSD поразрядными сортировками?»
- **Ответ:** «LSD (Least Significant Digit) начинает обработку с младших цифр (единиц) и двигается к старшим. Он требует обязательной устойчивости на каждом шаге, но не требует рекурсивного разделения массивов на корзины. MSD (Most Significant Digit) начинает со старших цифр, делит массив на непересекающиеся подмассивы (корзины) и рекурсивно сортирует каждую корзину отдельно, что требует дополнительного расхода памяти под стек рекурсии».

### Вопрос 3. «Почему в HeapSort мы начинаем построение кучи с индекса `(n - 2) // 2`, а не с `n - 1`?»
- **Ответ:** «Потому что элементы с индексами от `n // 2` до `n - 1` являются листьями двоичного дерева (у них нет потомков: для них $2i + 1 \ge n$). Лист сам по себе уже тривиально является корректной кучей размера 1. Индекс `(n - 2) // 2` соответствует родителю последнего листа массива `a[n - 1]`. Все узлы правее него просеивать бессмысленно».

### Вопрос 4. «Почему HeapSort является нестабильным алгоритмом? Приведите пример».
- **Ответ:** «Нестабильность возникает из-за обмена корня кучи `a[0]` с последним элементом `a[end]`, а также из-за скачков при просейке вниз.  
  Например, рассмотрим кучу из элементов с одинаковыми ключами, но разными метками: `[(5, 'a'), (5, 'b')]`.  
  На шаге извлечения максимум `(5, 'a')` меняется с последним элементом `(5, 'b')`. В результате массив становится `[(5, 'b'), (5, 'a')]` — исходный порядок меток инвертирован».

### Вопрос 5. «Почему в MergeSort вспомогательная память $O(n)$, а в QuickSort $O(\log n)$?»
- **Ответ:** «MergeSort при объединении двух половин вынужден создавать новый массив размера $n$, чтобы не перезаписать ещё не сравненные элементы исходных списков. QuickSort разбивает массив на месте (in-place) перестановками элементов, а память $O(\log n)$ тратится исключительно на стек границ подзадач `(lo, hi)`».

### Вопрос 6. «Как вы экспериментально доказали, что неустойчивый проход ломает RadixSort?»
- **Ответ:** «В процедуре самопроверки `check_radix_stability()` мы создали функцию `unstable_digit_pass()`, которая расставляет элементы по цифре в прямом порядке (`for x in arr:` вместо `reversed(arr)`). На входе `[21, 12, 11]` сортировка по младшему разряду даёт `[21, 11, 12]`, а неустойчивый проход по десяткам выдаёт `[12, 11, 21]` вместо `[11, 12, 21]`, доказывая необходимость устойчивости».
